## สิ่งที่เจอ (เรียงจากหนักไปเบา)

### 1. SD เสียตอนอยู่นอกบ้าน เครื่องจะเปิด Wi-Fi ทุกนาที
`status.ino:71-78` ตั้ง `sdAlertSent = true` เฉพาะตอนที่ `connectWiFi()` สำเร็จ
ถ้าหา hotspot ไม่เจอ `sdAlertSent` จะยังเป็น false ทุกรอบที่ตื่น (ทุก 60 วิ) เงื่อนไข `!sdAlertSent` ที่ `step11_tidy.ino:76` จะเป็นจริงอีก แล้วเปิด Wi-Fi ค้างรอ 6 วิ (`WIFI_TIMEOUT_MS`)
ซึ่งเป็นสิ่งที่คอมเมนต์ใน `state.h:17` บอกว่าตัวแปรนี้มีไว้กันไม่ให้เกิด
- แก้: ย้าย `sdAlertSent = true;` ออกมานอก `if (connectWiFi())` แล้วรอบถัดไปจะรอตาม `nextUploadUs` ซึ่ง `wifiOffUntil()` ตั้งไว้ 30 นาทีอยู่แล้ว
- ทดสอบ: ถอด SD ออก ปิด hotspot แล้วดู Serial ว่ามีการต่อ Wi-Fi ทุกนาทีหรือเปล่า

### 2. แจ้ง server ไม่สำเร็จแต่เครื่องเข้าใจว่าแจ้งแล้ว
ในจุดเดียวกัน ถ้าต่อ Wi-Fi ได้แต่ POST `/api/status` ไม่ได้ 200 (server ปิดอยู่) โค้ดก็ยังตั้ง `sdAlertSent = true` เพราะ `sendStatus()` ไม่คืนผลลัพธ์
ผลคือการแจ้งครั้งต่อไปเลื่อนไปอีก 30 นาที แต่ตัวนับยังสะสมไว้ จึงไม่มีข้อมูลหาย แค่แจ้งช้า
- แก้ (ถ้าจะแก้): ให้ `sendStatus()` คืน `bool` แล้วตั้ง `sdAlertSent` ตามผลนั้น แต่ต้องระวังอย่าให้ไปขัดกับการแก้ข้อ 1

### 3. กล้องเสียแล้วจะไม่มีการส่งไฟล์หรือแจ้งสถานะเลย
`step11_tidy.ino:88-93` ถ้า `initCamera()` ล้มเหลวจะนับ `camFailCount` แล้ว `goToSleep()` ทันที เส้นทางนี้ข้าม `tryUpload()` ไป
ผลคือถ้ากล้องเสียถาวร (เช่นสายแพหลุด):
- server จะไม่ได้รับ `cam_fail` เลย เพราะสถานะถูกส่งจากใน `tryUpload()` เท่านั้น
- ไฟล์ที่ค้างอยู่บน SD ก็ส่งไม่ออก ต่อให้กดปุ่มค้างสั่งส่งก็ไม่ได้
- ต่างจากกรณี SD เสีย ที่ยังมี `statusOnlyRound()` ไว้แจ้ง server
- แก้: ตอนกล้องเสียยังให้ทำขั้น 5 (`if (nowUs() >= nextUploadUs) tryUpload();`) ก่อนหลับ (`tryUpload()` เรียก `esp_camera_deinit()` ซึ่งเรียกตอนที่ init ไม่สำเร็จได้ แต่ควรเช็กให้แน่ใจ)

### 4. เปิดเครื่องตอน SD เสีย แล้วเลขภาพจะเริ่มนับใหม่จาก 1
`photoNumber = loadLastNumber()` (`:81`) ทำเฉพาะใน `if (coldBoot)` ซึ่งอยู่**หลัง**จุดเช็ก SD (`:72`)
ถ้าตอนเปิดเครื่องหรือกด RESET SD เปิดไม่ได้ (เช่นการ์ดหลวม แบบที่เกิดเมื่อ 20 ต.ค.) เครื่องจะหลับไปก่อนถึงบรรทัดอ่านเลข พอตื่นรอบถัดไปก็ไม่ใช่ coldBoot แล้ว จึงไม่มีการอ่าน `counter.txt` อีกเลย `photoNumber` ค้างอยู่ที่ 0 (`state.h:6`)
พอ SD กลับมาใช้ได้ ช่วงที่ยังไม่ได้เวลาจาก server (`timeValid` = false หลัง coldBoot) ภาพจะได้ชื่อ `photo_00001.jpg`, `photo_00002.jpg` ... ซ้ำกับชื่อเดิม:
- บน SD: `FILE_WRITE` จะเขียนทับภาพเก่าชื่อเดียวกันที่ยังไม่ได้ส่ง ภาพเก่าหาย
- บน server (`server/board.py:41-53`): ชื่อที่ไม่มีเวลาจะลงโฟลเดอร์ตามวันที่อัปโหลด ถ้าเป็นวันเดียวกับภาพเก่าก็จะเขียนทับ
- `markSent()` (`upload.ino:172`): ถ้าใน `/sent` มีชื่อนี้อยู่แล้ว rename จะไม่ผ่าน แล้วไฟล์จะถูกลบจาก SD
- `counter.txt` จะถูกเขียนทับด้วยเลขใหม่ที่น้อยกว่า
- คลิปไม่โดน เพราะ `nextClipFolder()` เช็กชื่อใน `/sent` ด้วย
- แก้: ใช้ตัวแปร RTC ตัวใหม่ (เช่น `counterLoaded`) แทนการผูกกับ `coldBoot` ให้อ่าน `counter.txt` ครั้งแรกที่เปิด SD ได้ หรือให้ `takeTimelapsePhoto()` ข้ามชื่อที่มีอยู่แล้ว
- ทดสอบ: ถอด SD ออก กด RESET รอ 1 นาที เสียบ SD กลับ แล้วดูชื่อภาพใน `log.txt`

### 5. เล็กน้อย (ไม่ต้องรีบแก้)
- `markSent()` (`upload.ino:172-178`): ถ้า `SD.rename` ไม่ผ่านด้วยสาเหตุอื่นที่ไม่ใช่ชื่อซ้ำ ไฟล์จะถูกลบจาก SD (server ได้ไปแล้ว ไฟล์ไม่หาย แต่สำรองบนการ์ดหายไป)
- `uploadAll()` ส่ง `log.txt` ทั้งไฟล์ทุกรอบ และ log ไม่เคยถูกตัด ไฟล์โตขึ้นวันละ ~90 KB เวลาส่งจะนานขึ้นเรื่อยๆ (ยังไม่เกินเพดาน 60 วิในเร็วๆ นี้)
- `goToSleep()` (`step11_tidy.ino:156`) วนรอให้ปล่อยปุ่ม ถ้าปุ่มค้างหรือช็อตลง GND เครื่องจะวนอยู่ตรงนั้นจน watchdog (3 นาที) รีเซ็ต

### 6. เล็กน้อยในฝั่งคลิป
- `recordClip()` (`clip.ino:13-16`): ถ้า `SD.mkdir` ไม่ผ่าน จะ return ออกไปโดยไม่เรียก `i2s.end()` (ไม่มีผลเสียเพราะเดี๋ยวก็หลับลึก)
- ภาพในคลิปที่บันทึกไม่ผ่านไม่ถูกนับเข้า `photoFailCount` (นับเฉพาะ timelapse) server จึงไม่เห็น

## ตรวจแล้วไม่พบปัญหา
- `syncTime()` เลื่อน `nextPhotoUs`/`nextUploadUs` ตามเวลาที่กระโดด ถูกต้อง
